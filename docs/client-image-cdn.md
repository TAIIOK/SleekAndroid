# Client: выбор CDN для постеров аниме (`X-Image-CDN`)

Спека для iOS / Android / Web-клиентов. Бекенд **не проксирует** картинки — в JSON приходят прямые URL на yani CDN. Хост зависит от региона и от того, что доступно клиенту.

## Проблема

Постеры YummyAnime отдаются с двух хостов с разной доступностью:

| Хост | Типичная доступность |
|------|----------------------|
| `imgproxy.yani.tv` | РФ / СНГ |
| `static.yani.tv` | Европа и другие регионы вне СНГ |

Старый хост `img.yani.tv` тоже встречается в данных; бекенд переписывает его вместе с остальными.

Клиент с VPN может оказаться «в другой стране» относительно реального местоположения — поэтому **надёжный способ** — явный заголовок от клиента.

## Контракт

### Заголовок

```http
X-Image-CDN: static
```

или

```http
X-Image-CDN: imgproxy
```

| Значение | Хост в `poster.*` URL |
|----------|------------------------|
| `static` | `https://static.yani.tv/...` |
| `imgproxy` | `https://imgproxy.yani.tv/...` |

- Регистр не важен (`Static` / `IMGPROXY` допустимы).
- Неизвестное значение игнорируется → срабатывает geo-fallback на сервере.
- Заголовок нужно слать **на все запросы**, которые возвращают аниме с постерами (каталог, детали, рекомендации, Jellyfin-совместимые image URL и т.п.).

### Что меняется в ответе

Формат JSON не меняется. Меняется только host в полях:

```json
{
  "poster": [
    {
      "source": "https://imgproxy.yani.tv/...",
      "preview": "https://imgproxy.yani.tv/...",
      "thumbnail": "https://imgproxy.yani.tv/...",
      "optimized": "https://imgproxy.yani.tv/..."
    }
  ]
}
```

Клиент **не должен** сам переписывать host после ответа, если уже отправил `X-Image-CDN`.

### Поведение без заголовка (fallback)

Если `X-Image-CDN` нет, бекенд выбирает хост по стране:

1. `CF-IPCountry` (Cloudflare), иначе `X-Country-Code` (reverse-proxy)
2. Страны СНГ (по умолчанию: `RU`, `BY`, `KZ`, `AM`, `AZ`, `KG`, `MD`, `TJ`, `UZ`) → `imgproxy`
3. Остальные известные страны → `static`
4. Страна неизвестна → `static` (конфиг `images.default_host`)

Старым клиентам без заголовка постеры всё равно придут, но при VPN geo может ошибиться.

## Что должен сделать клиент

### 1. Probe при старте (один раз)

На холодном старте (или после смены сети / VPN) проверить доступность обоих хостов.

Рекомендуемый порядок:

1. Взять короткий известный URL постера (можно захардкодить probe-asset или взять любой постер из предыдущего кэша).
2. Собрать два URL с одинаковым path:
   - `https://imgproxy.yani.tv/<path>`
   - `https://static.yani.tv/<path>`
3. Сделать `HEAD` (или лёгкий `GET`) с таймаутом **2–3 секунды** на каждый.
4. Считать хост рабочим при HTTP `2xx` / `3xx` (и при успешном соединении без TLS/DNS ошибки).

Параллельный probe обоих хостов предпочтительнее последовательного.

### 2. Выбор preference

| Результат probe | Preference |
|-----------------|------------|
| Оба доступны | Предпочитать `imgproxy` для RU/СНГ locale, иначе `static`; либо тот, кто ответил быстрее |
| Только `imgproxy` | `imgproxy` |
| Только `static` | `static` |
| Оба недоступны | Не слать заголовок (пусть сработает серверный fallback) или оставить последний успешный |

### 3. Persist

Сохранить preference локально (UserDefaults / SharedPreferences / Keychain не нужен):

- ключ, например: `image_cdn_preference` = `"static"` | `"imgproxy"`
- опционально: timestamp последнего успешного probe
- опционально: тип сети / VPN state, чтобы перезапускать probe при смене

### 4. Слать заголовок на API

Добавить во **все** authenticated/guest API-клиенты (общий HTTP interceptor / `URLSession` adapter):

```http
X-Image-CDN: <preference>
```

Пример:

```http
GET /api/animes/123 HTTP/1.1
Host: api.example.com
Authorization: Bearer …
X-Image-CDN: imgproxy
```

### 5. Re-probe

Повторять probe когда:

- смена VPN on/off или сервера VPN
- смена Wi‑Fi ↔ cellular (опционально)
- массовые ошибки загрузки постеров (например N подряд failed image loads) → re-probe и обновить preference
- раз в сутки / при major app update (опционально)

После смены preference следующий API-запрос уже вернёт URL с новым host. Уже загруженные в UI картинки можно оставить в кэше; новые экраны подтянут новые URL.

## Минимальный чеклист для релиза клиента

- [ ] HTTP-слой умеет выставлять `X-Image-CDN`
- [ ] Probe `static` + `imgproxy` на старте
- [ ] Preference сохраняется между запусками
- [ ] Re-probe при VPN / сетевых сменах
- [ ] Постеры грузятся с URL из ответа API as-is (без клиентского host-rewrite)
- [ ] Старый клиент без заголовка не ломается (серверный fallback)

## Не делать

- Не проксировать картинки через AniVerse API
- Не хардкодить всегда `imgproxy` или всегда `static`
- Не полагаться только на geo IP на клиенте, если есть VPN
- Не дублировать оба URL в UI-моделях — бекенд отдаёт один набор полей

## Тест-план

1. Без заголовка из РФ-like сети → в `poster.source` ожидается `imgproxy.yani.tv` (если proxy отдаёт `CF-IPCountry: RU`).
2. `X-Image-CDN: static` → все yani-постеры на `static.yani.tv`.
3. `X-Image-CDN: imgproxy` → все yani-постеры на `imgproxy.yani.tv`.
4. Включить VPN в «другую» страну, сделать probe, убедиться что preference и URL совпадают с доступным хостом.
5. Открыть каталог / карточку аниме / (если используется) Jellyfin image endpoint — везде один и тот же host.
